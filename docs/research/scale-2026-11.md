# 수천~수만 명이 써도: 수용량·비용·넘침 처리 (2026-11-13)

운영자 요구: "수천 수만 명이 lecpage를 써도 최대한 받아라. 퀄리티가 떨어지면 절대 안 된다. 무료로 운영할 때도 최대한 많은 사람이 쓰게, 무료 한도에 닿으면 Vercel 등으로 안내하거나 내가 유료 결제."
구현: `hosting/src/{fair,capacity,gate,site,room,index,config}.js`, 관리 화면(`hosting/public/admin/`), `hosting/scripts/capacity-model.mjs`(표), 시험 `hosting/test/{scale,fair,capacity}.test.mjs`. 운영 안내는 [`hosting/README.md`](../../hosting/README.md) §4.

## 1. 결론

- **운영자 돈이 드는 곳은 바로 배포 서버 하나이고, 그 안에서도 거의 전부가 '참여 기능 방'(특히 웹소켓이 막힌 학교망의 묻기)입니다.** 사이트 보기는 Pages 정적 요청이라 무료·무제한, 앱은 정적 자산이라 무료·무제한, AI·일반 배포는 사용자 몫입니다(§2).
- 무료로 버티는 크기(가장 바쁜 날 모든 한도가 60% 아래, 강사 한 명이 한 달 연수 2회·참가자 40명·참여 기능 50%·그중 학교망 40%, 런타임은 2026-11-13부터 긴 대기가 기본):
  - 참여 기능 방까지 운영자가 맡으면 **월 활성 강사 약 90명**(낮음 1회·20명이면 약 250명, 높음 4회·100명이면 약 20명).
  - 참여 기능 방은 넘칠 때 강사 계정(Cloudflare·Supabase, 강사마다 무료 한도가 따로)으로 넘기고 사이트만 맡으면 **약 5,500명**(먼저 차는 것은 저장 5GB·DO 행 쓰기).
- **Workers Paid(월 $5)** 로 올리면 하루 한도가 없어 멈추지 않습니다. 월 비용(같은 가정, 유료 기본 = 긴 대기를 Worker가 대신): **1천 명 약 $7, 1만 명 약 $43, 10만 명 약 $460**. 참여 기능 방을 강사 계정으로 넘기면 10만 명도 약 $15(§4).
- 그래서 기본 설계는 **"사이트는 늘 바로 배포(품질 그대로), 참여 기능 방은 그날 몫 안에서만 맡고 넘치면 강사 계정으로"** 입니다. 사이트 파일은 어디로 넘겨도 같은 파일이라 품질이 같습니다.
- 무료 하루 한도는 Worker 요청·DO 요청·DO duration이 **따로**라, 서버는 셋 중 가장 빠듯한 것으로 단계를 정합니다. 긴 대기가 기본이 되면서 참가자가 적은 연수가 여럿인 날은 요청보다 duration이 먼저 찰 수 있어(20명 연수 28개 = 요청 60%·duration 194%), 방이 깨어 있던 시간을 재서 넣고 duration이 빠듯해지면 긴 대기를 Worker가 대신 맡게 했습니다(§6).
- 유료로 올려도 남는 벽: **Cloudflare API 속도 제한(토큰마다 5분에 1,200번)**. 배포 한 번에 Pages API를 약 5번 부르므로, 배포가 몰리는 바쁜 날 기준 월 활성 강사 약 1.5만~2만 명에서 닿습니다. 서버가 5분 창으로 줄을 세우고(§5), 그 너머는 Workers for Platforms나 Cloudflare에 한도 상향 요청이 필요합니다(§9).

읽는 법:
- 무료에서 먼저 차는 것은 **요청 수(Worker·DO, 각 하루 10만)**, 그다음이 방 안 긴 대기의 **duration**입니다. 참여 기능이 없으면 저장 5GB(사이트가 60일 남음)와 행 쓰기가 다음입니다.
- 긴 대기를 **방 안에서** 기다리면 무료에서는 남는 duration 몫을 써서 요청을 아끼므로 더 많이 받지만(89명 대 46명), 유료에서는 duration 값 때문에 두 배 넘게 비쌉니다. 그래서 `POLL_RELAY=auto`: 유료는 늘 Worker가 대신, 무료는 방 안에서 기다리다가 오늘 duration이 50%를 넘으면 Worker가 대신(§6).
- 유료 비용은 사용자 수에 거의 정비례(1만 명당 약 $4, 사이트만이면 거의 0)입니다.
- 웹소켓 닫힘 이벤트가 DO 요청으로 세지 않는다면 'Worker가 대신'의 DO 요청은 표의 약 절반이라 유료 비용이 더 내려갑니다(실제 계정에서 확인할 것, §9).

## 5. 품질을 지키는 넘침 처리

원칙: **오늘 진행 중인 연수와 이미 배포한 사이트는 절대 깨지지 않는다.** 한도에 가까워지면 '새로 만드는 사람'부터, 같은 파일 그대로 강사 계정으로 넘깁니다. 넘기는 길은 앱에 이미 있습니다(내 계정에 배포하기 체크리스트·바로 다시 배포).

### 5.1 단계(`hosting/src/fair.js`, Gate가 매 요청 판단)

'쓴 몫' = 오늘 Worker 요청 + 오늘 아직 끝나지 않은 예약 연수의 남은 어림(예약형 수용량).

| 단계 | 조건(무료) | 새 사이트 | 새 참여 기능 방 | 다시 배포·이미 연 방·사이트 보기 |
|---|---|---|---|---|
| `open` | 45% 아래 | 받음 | 받음 | 됨 |
| `tight` | 45~60% | **연수 날짜가 14일 안(예약)인 것만** | 같음 | 됨 |
| `full` | 60% 이상, 저장 공간 참, 하루 상한 참, Pages API 줄 서기 | 강사 계정으로 | 강사 계정으로 | 됨 |
| `paused` | 운영자가 멈춤 | 강사 계정으로 | 강사 계정으로 | 보기만(다시 배포 503) |

유료(`PLAN=paid`)는 예산이 없어 요청 수로는 막지 않고, 저장·하루 상한·Pages API·멈춤만 봅니다.

### 5.2 공정 몫: 계정이 없으니 무엇으로 셀까

| 무엇으로 | 장점 | 약점 | 정함 |
|---|---|---|---|
| IP | 앱 고칠 필요 없음 | 학교 하나가 IP 하나: 강사 연수(30명이 한 공유기)에서 6번째부터 막힘. 휴대폰 망은 여럿이 한 IP | 기기 표가 없을 때만(예전처럼 시간 6·하루 20) |
| **기기 표**(앱이 기기에 둔 무작위 값) | 사람 하나에 가까움. 공유기를 같이 써도 따로 셈 | 지우거나 바꾸면 새 기기 | **기기마다 하루 5개(유료 10)**. 이때 같은 IP는 시간 30·하루 60으로 넉넉히(바꿔 가며 쓰는 것을 묶음) |
| 사이트 수정 열쇠 | 다시 배포는 이미 사이트마다 시간 30번 | 새 사이트는 열쇠가 없음 | 다시 배포에만 |
| 하루 전체 상한 | 저장·검토 부담을 묶음 | 선착순 | Pages 보기 하루 200개(유료 1,000), Worker 보기 30개(유료 300). 방 100개(유료 1,000) |

기기 표·IP는 그대로 두지 않고 날짜와 함께 해시해 그날만 셉니다(예전 IP 처리와 같음). 동시에 50명이 만들어도 하루 상한·기기 몫이 정확히 지켜짐을 시험했습니다(`fair.test.mjs` 경합, 확인과 적기 사이에 기다림이 없음).

### 5.3 예약된 연수 우선, 오래 쓸 사이트는 강사 계정

- 붐빌 때(`tight`) 날짜가 가까운 연수부터 받습니다. 예약은 앱이 이미 보냅니다(`booking`).
- 오늘 아직 끝나지 않은 예약 연수의 남은 몫만큼 새 일을 일찍 멈춰, 그 연수가 오후에 깨지지 않게 합니다(예전부터).
- 예약 없이 만든 사이트(체험·오래 쓸 사이트일 수 있음)에는 `advice: { code: 'long_term' }`을 같이 줍니다: "오래 쓸 사이트는 내 계정에 배포하면 보관 기간 제한이 없어요". 막지는 않습니다(체험은 바로 배포가 가장 좋음).

### 5.4 참여 기능만 넘기기(split)

그날 예약된 참여 기능 몫이 차면, 예전에는 **사이트까지** 거절했습니다. 이제 앱이 `caps: ['split']`을 보내면 **사이트는 바로 배포로 받고 참여 기능 방만** 강사 계정(Cloudflare·Supabase)으로 넘기라고 알립니다(`live: { ok: false, reason: 'booked', next: ['cloudflare','supabase'] }`). 사이트는 Pages라 그날 아무리 붐벼도 열리므로 품질 손해가 없습니다. 예전 앱(caps 없음)에는 예전처럼 거절해 앱이 처음부터 내 계정으로 안내하게 합니다(그래야 올린 뒤에야 막히는 일이 없음).

### 5.5 Pages API 줄 서기

배포가 몰려 Cloudflare API 한도(5분 1,200번)를 넘으면 그 토큰의 **모든** API가 5분 막혀 가리기·지우기까지 멈춥니다. 그래서 Gate가 5분 창(`PAGES_API_BUDGET`, 기본 900 = 75%)으로 '목록 받기' 때 이번 공개가 쓸 어림(공개 7 + 큰 파일 2개씩)을 맡기고, 넘치면 `rate_limited` + `reason: 'pages_api'` + `retry-after`로 1~5분 뒤 다시 하게 합니다. 그래도 429를 받으면 5분 동안 새 배포를 줄 세우고 운영자에게 알립니다.

### 5.6 앱이 받는 신호

| 어디 | 무엇 |
|---|---|
| `GET /api/info` → `capacity` | `{ state, reason, newSites, newRooms, onlyBooked, pct, resetAt, retryAt?, message_ko, next: ['cloudflare','vercel','github','netlify'], liveNext: ['cloudflare','supabase'], siteDays }` (isolate 20초·브라우저 30초 기억) |
| `GET /api/status` | 위 `capacity` + `site.booking.liveDenied`·`liveNext` |
| `POST /api/sites` 201 | `share: { scope: 'device'\|'ip', left }`, (split) `live`, (예약 없음) `advice` |
| `POST …/deploys` 200 | (예약을 바꿨고 그날 방이 찼으면, split) `live` |
| 429·503·507 오류 | `reason`(`paused`·`budget`·`tight`·`daily_cap`·`room_cap`·`storage`·`pages_api`·`booked`·`device`·`ip`·`ip_hour`), `scope`(`you` = 이 기기·주소만 / `everyone`), `next`, (방) `liveNext`, `retryAt`, `message_ko` |

## 6. 운영 효율: 무료로 더 받기

| 무엇 | 결과 |
|---|---|
| 런타임 Pages 열쇠 미리 계산, `robots.txt` 받지 않음 | 새 사이트 Worker 요청 −8, DO −8, Pages API −7 |
| 작은 파일은 배포 때 한 번에(메모리, 512KB·사이트당 16MB까지) | Pages API −7~14/사이트, 행 쓰기 늘지 않음. 객체가 그새 내려가면 `missing_blobs`로 그것만 다시 |
| Gate 호출 합치기 | 목록 −1, 방 묶기 −1 DO 요청 |
| Gate 저장량 합계를 메모리로 | 예전에는 새 사이트·목록·방·배포마다 사이트 표 전체를 훑음(사이트 1만 개면 한 번에 1만 행 읽기, 무료 하루 500만 행 → 배포 수백 번에 바닥). 이제 깨어날 때 한 번 |
| `/api/info` 기억 | 앱이 켜질 때마다 Gate를 깨우지 않음 |
| 긴 대기를 Worker가 대신(`POLL_RELAY=auto`) | 방은 잠들 수 있는 웹소켓 하나만 열고 바로 잠듦 → duration ≈ 0. 대신 한 번에 DO 요청 1~2. **유료는 늘 켬(1만 명 기준 월 $107 → $43)**. 무료는 남는 duration 몫으로 방 안에서 기다리다가(요청을 아껴 89명 대 46명) 오늘 duration이 50%를 넘으면 그때부터 Worker가 대신 |
| 하루 한도를 세 몫으로 | 단계(open·tight·full)·알림·관리 화면을 Worker 요청·DO 요청(`ds`·`dr`·`g`·`gt`·`rc`)·DO duration(방이 깨어 있던 초 `aw` × 0.125GB) 중 가장 빠듯한 것으로. 방은 SSE·방 안 긴 대기로 깨어 있던 시간을 10분마다·끝날 때 Gate에 알림(2시간 방이 Gate 요청 12번쯤). 무료에서 duration 60%부터 새 SSE는 503으로 돌려보내 런타임이 긴 대기로 내려감. 예약 어림도 세 몫 중 큰 것 |
| 이미 있던 것 | 웹소켓 Hibernation + `ping` 자동 응답(깨우지 않음), 빈 방은 알람이 지움, 묻기 간격 권고(`X-Lec-Poll-Ms` 50%면 10초·80%면 20초), 예산 85%부터 이용 합계 버림, 없는 주소 1분 기억 |

SSE(웹소켓은 막히고 SSE는 되는 학교망)는 연결이 열린 동안 방이 깨어 있어 duration을 씁니다(방 하나 한 시간 450 GB-s, 무료 하루 약 29방-시간). 요청은 묻기의 수십 분의 일이라 무료에서는 묻기보다 훨씬 많이 받으므로 런타임 순서(웹소켓 → SSE → 긴 대기)는 그대로 두고, duration이 빠듯해질 때만 새 SSE를 긴 대기로 돌립니다. SSE도 Worker가 대신 들고 있으면 duration이 0이 되지만, 무료 Worker CPU(요청당 10ms)를 긴 연결 내내 나눠 써야 해 넣지 않았습니다(유료만 켜는 선택지로 남김).

## 7. 부하 시험과 병목

`hosting/test/scale.test.mjs`(로컬 workerd 한 프로세스, 4코어. 응답 시간은 이 기계의 값이라 실제와 다르고, 확인한 것은 맞게 도는지와 요청 수):

| 시나리오 | 결과 |
|---|---|
| 강사 50명이 동시에 배포(참여 기능 방 묶기·예약) | 실패 0, 7초, 요청 p95 1.65초 |
| 방 50개 × 참가자 60명 = 3,000명이 한꺼번에(셋 중 하나씩 웹소켓·묻기·긴 대기) | 실패 0, 5xx 0, 질문·참가자 빠짐 0, Worker 17,901·DO 18,151 요청 |
| 큰 방 하나에 300명(강당 연수: 묻기·긴 대기) | 실패 0, 질문 300·참가자 300 모두 들어감, p95 2.6초 |
| 동시 만들기 50건, 하루 상한 30 | 정확히 30개(경합 없음) |

**전역 Gate DO는 병목인가**: 아닙니다. Gate는 새 사이트·목록·방·배포·상태와 하루 숫자 모으기만 받고 참가자 요청은 받지 않습니다. 부하 시험에서 DO 요청 중 Gate 몫 **1.1%**(숫자 모으기 포함 약 2%). 10만 명이 가장 바쁜 날(하루 약 1억 요청이 8시간에 몰림 ≈ 초당 3,400)에도 Gate는 초당 약 70건으로 공식 '객체 하나 초당 1,000건'(durable-objects/platform/limits)의 7%입니다. 그래서 **샤딩하지 않았습니다.** 대신 Gate가 요청마다 하던 비싼 일(사이트 표 전체 훑기)을 없앴습니다(§6). 방 DO는 연수 코드마다 하나라 원래 나뉘어 있고, 300명 방도 초당 수십 건입니다.

샤딩이 필요해지는 때: 하루 숫자 모으기는 isolate마다 50건씩이라 Worker가 초당 5만 건을 넘으면 Gate가 초당 1,000건에 닿습니다(월 활성 강사 수백만 명 규모). 그때는 하루 숫자를 시간별 Gate 여럿(`gate:<시간 % N>`)에 나눠 적고 관리 화면이 합치면 됩니다.

## 8. 운영자 판단 도구

관리 화면 맨 위 한 줄(`capacity.js` `forecast()`, 지난 7일·28일 하루 숫자):

| 권하는 행동 | 언제 |
|---|---|
| **유료 전환을 권해요**(월 약 $N) | 무료이고, 최근 7일 중 2일 이상 하루 한도의 50%를 넘었거나 28일 추세로 7일 안에 60%(새 사이트를 받지 못하는 선)에 닿을 때 |
| **하루 상한을 올려도 돼요** | 요청은 넉넉한데(가장 많은 날 30% 아래) 최근 7일 중 2일 이상 하루 새 사이트 상한에 닿았을 때(유료도) |
| **새 배포 멈추기를 검토하세요** | 오늘 새 사이트가 20개 넘고 평소의 3배를 넘을 때(스팸·이상한 몰림) |
| 지금은 할 일 없음 | 그 밖(무료로 충분, '이 추세면 약 N일 뒤 빠듯' 함께) |

타일: 지금 단계·까닭, 오늘 DO 요청(어림)·Gate 몫, Pages API 5분 창, 이번 달 추세(30일 어림), 무료가 빠듯해지는 날(45%·60%), 유료로 올리면 월(항목별).

알림(웹훅): 하루 예산 **45·60·80·95%**(단계와 같게: 예약한 연수만 → 새 일 멈춤 → 묻기 20초 → 곧 한도. Pages 보기면 "사이트는 열려요"), 새 사이트가 하루 상한의 80%, 저장 80%, Pages API 429, 그리고 무료에서 '유료 전환을 권해요'가 뜨면 일주일에 한 번.

## 9. 운영자가 언제 무엇을

| 언제 | 할 일 |
|---|---|
| 처음 | `npm run setup`(Pages 보기가 기본). 무료로 시작 |
| 관리 화면이 '유료 전환을 권해요' 또는 45% 알림이 한 주에 두 번 넘게 | Workers Paid(월 $5)로 올리고 `PLAN=paid`. 비용은 관리 화면 '유료로 올리면 월' |
| 유료로 안 올리고 버틸 때 | 그대로 두면 됨: 붐비는 날은 예약한 연수만, 넘치면 강사 계정으로 자동 안내. 이상한 몰림이면 [새 배포 멈추기] |
| '하루 상한을 올려도 돼요' | `DAILY_SITE_CAP` 올림(무료는 저장 5GB를 봐 가며) |
| 저장 80% 알림 | 무료: 그대로 두면 다 찬 날부터 새 사이트는 강사 계정으로. 유료: `MAX_TOTAL_BYTES` 올림(GB-월 $0.20) |
| Pages API 429 알림이 잦음(월 활성 1.5만 명 넘음) | `PAGES_API_BUDGET`을 낮춰 줄을 더 일찍 세우고, Cloudflare에 API 한도 상향 문의 또는 Workers for Platforms 검토(월 $25~, 프로젝트 제한 없음) |
| 여러 무료 계정으로 한도를 쪼개 늘리기 | **하지 않음**(약관 위반 소지). 같은 계정의 API 토큰을 여러 개 만들어 속도 제한을 피하는 것도 하지 않음 |

실제 계정에서 확인할 것(이번에 못 함): Pages 직접 올리기(Direct Upload) 배포가 '빌드 월 500회'에 드는지(든다면 무료 계정은 월 500번 공개가 상한 → 바로 배포의 진짜 한도가 됨), 자산 API(JWT)가 1,200/5분에 같이 세는지, 웹소켓 닫힘 이벤트가 DO 요청으로 세는지, 직접 올리기 배포가 Workers 쪽으로 옮겨질 때의 변화.

## 10. 앱 화면 문구 변경 목록(화면 작업자에게)

서버는 위 신호를 이미 줍니다. 앱 쪽에서 할 일:

1. **기기 표 보내기**: 처음 켤 때 무작위 22자(base64url)를 만들어 저장하고 `POST /api/sites` 본문에 `device`로. 학교 공유기 하나에 강사 30명이 있어도 막히지 않습니다.
2. **`caps: ['split']` 보내기**(아래 5를 붙인 뒤): 그날 방이 차도 사이트는 바로 배포로.
3. 배포 화면을 열 때 `info.capacity`로 처음부터 알맞은 길:
   - `tight`: "오늘은 바로 배포가 붐벼요. 연수 날짜가 2주 안이면 날짜를 넣어 주세요(먼저 받아요). 아니면 내 계정에 배포해 주세요(같은 파일 그대로예요)."
   - `full` + `budget`: "오늘은 바로 배포 자리가 다 찼어요. {resetAt 한국 시각}에 다시 받아요. 지금 배포하려면 내 계정에 배포해 주세요(같은 파일 그대로예요)." → `next` 순서로 체크리스트
   - `full` + `daily_cap`: "오늘 바로 배포 새 사이트 자리가 다 찼어요. …"(위와 같은 길)
   - `full` + `pages_api`: "배포하는 사람이 한꺼번에 많아 잠깐 줄을 서고 있어요. {retryAt}쯤 자동으로 다시 해 볼게요." + 자동 다시 시도
   - `paused`: "운영자가 잠시 바로 배포를 멈췄어요. 이미 배포한 사이트는 그대로 열려요."
4. 오류의 `scope`로 말을 가름: `you` → "이 기기(이 학교 인터넷)에서 오늘 만들 수 있는 새 사이트를 다 썼어요. 이미 만든 사이트는 다시 배포할 수 있어요." / `everyone` → "오늘은 바로 배포가 다 찼어요." 둘 다 서버의 `message_ko`를 그대로 써도 됨.
5. 201·deploys의 `live.ok === false`: "그날은 바로 배포 참여 기능 방이 다 찼어요. 사이트는 바로 배포 그대로 두고, 참여 기능만 내 Cloudflare(무료) 또는 Supabase로 연결해요." → 참여 기능 연결 체크리스트(`liveNext` 순서). 사이트를 그 설정으로 다시 빌드해 공개.
6. 201의 `advice.code === 'long_term'`(예약 없음): 배포 결과에 한 줄 "오래 쓸 사이트면 내 계정에 배포하면 기간 제한이 없어요(바로 배포는 마지막으로 배포한 날부터 {siteDays}일)."
7. `share.left`가 0~1이면 작게: "이 기기에서 오늘 새 사이트를 {left}개 더 만들 수 있어요."
8. 연수 전날 점검: `status.site.booking.liveDenied`면 "이 연수의 참여 기능은 내 계정으로 연결해야 해요" 경고.

## 11. 런타임 쪽(학교망 작업자에게)

학교망 작업자가 main에 넣은 것(긴 대기 `wait=20`, `X-Lec-Poll-Ms`, `POLL_LONG` 기본 on)과 서버가 맞습니다. 서버 쪽에서 더한 것과 런타임이 알아 두면 좋은 것:

1. 긴 대기 응답은 서버가 방 안에서 기다리든 Worker가 대신 기다리든 모양이 같습니다(바뀐 것이 있으면 바로, 없으면 `wait`초 뒤 빈 snapshot). 런타임이 따로 할 일은 없습니다.
2. 무료에서 duration이 빠듯하면 `/events`(SSE)가 503 `busy`를 줍니다. 지금 런타임은 SSE 실패를 10분 건너뛰고 긴 대기로 내려가므로 그대로 맞습니다. 강사 화면 '묻기 방식' 한 줄에 "서버가 붐벼 묻기 방식으로 이어 가요"를 붙이면 좋습니다.
3. 긴 대기 한 번은 Worker 요청 1이고, 측정(1분 3.4)이 그대로 예약 어림에 쓰입니다. 조용할 때 2.4에 가깝게 하려면(글이 없을 때 다시 묻기 전 쉬는 틈 5초) 지금 값을 유지해 주세요.
